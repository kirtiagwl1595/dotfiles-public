# Decisions

Add a row for each design decision. Do not edit an accepted row, except to set its Status to `Superseded by D<n>`.

| ID | Status | Decision | Why | Options not taken | Supersedes | Sections changed |
|---|---|---|---|---|---|---|
| D1 | Accepted | The install adds to the user's files and never removes a user value. It asks before it replaces a weaker safety value, before it changes PATH and before it installs a tool. It saves a `<file>.bak` copy first. `--check` changes nothing. | The files belong to the user: `~/.claude/CLAUDE.md`, `~/.claude/settings.json` and `~/.gitconfig` hold their own rules and keys. A run that is safe to repeat and easy to undo gets used. | Overwrite the files with the repo copy: it destroys user values. Add a value silently when it is weaker than the safe one: the user would not know. | none | README.md, GUIDE.md section 2 |
| D2 | Accepted | The git defaults load through an `[include]` of `git/config.shared` at the top of `~/.gitconfig`. The file sets no name, email, signing key or credential helper. `core.excludesFile` is set only when the user has none. | In git, a later value wins. An include at the top lets every value in `~/.gitconfig` override the shared one. Identity is personal. | Copy the values into `~/.gitconfig`: later changes in the repo never arrive. An include at the bottom: the shared values would override the user. | none | README.md, GUIDE.md section 4 |
| D3 | Accepted | Every guard fails closed. Input that a guard cannot parse is blocked (exit 2). An error inside a check gives a deny. `py.sh` exits 2 when it finds no working Python 3.9 or later. | Claude Code lets a tool call through on any hook exit code except 2. A crash or a missing Python must not turn a guard off. | Exit 1 on error: the call passes. Skip the guard when Python is missing: the guards would be off with no warning. | none | docs/SETUP.md section 3 |
| D4 | Accepted | The guards run on all three OS, in Python 3.9 with the standard library only, started through `claude/hooks/py.sh`. They match paths in any case, with `\` or `/`, and with `~`, `$HOME`, `%USERPROFILE%` and `C:\Users\<name>`. | Native Windows has no sandbox, so the guards and the approval prompts are the only protection there. On Windows, `python3` can be the Microsoft Store stub, so the launcher tries `python3`, `py -3` and `python`, and checks the version. | Guards in bash only: they would not cover PowerShell. A Python dependency: it needs an install step before the guards work. | none | README.md, docs/SETUP.md section 3 |
| D5 | Accepted | Windows needs Git Bash. `install.py` stops when it finds none. | Claude Code runs hooks in Git Bash. Without it, the hooks run in PowerShell, `bash` is not found, and no guard runs. | Run the guards through PowerShell: a second launcher to keep right. Warn only: the user would think the guards run. | none | README.md |
| D6 | Accepted | The base settings use default mode, turn bypass mode off, and allow auto mode. Each session starts in default mode. `install.py` asks before it removes `permissions.disableAutoMode` from an older install. | Auto mode is useful and still keeps the deny rules and the guards. Starting in default mode means that the user chooses auto mode each time. Bypass mode skips the prompts that the setup relies on. | Disable auto mode: it removes a mode the user may want. Start in auto mode: a session would run on the classifier with no choice by the user. | none | README.md, GUIDE.md section 6 |
| D7 | Accepted | On macOS and Linux, the sandbox is on, with `failIfUnavailable`, and `gh`, `glab` and the plugin's `forge.sh` are in `excludedCommands`. They run outside the sandbox, so they ask in default mode. No allow rule skips that question. | The Go CLIs fail the macOS TLS check inside the sandbox and cannot read the keychain there. A silent sandbox that falls back to no sandbox would give a false sense of safety. | Run `gh` inside the sandbox: it fails. Add a CA variable or `--trusted-host`: it applies to every command. Allow the outside commands with a rule: the user would lose the question. | none | docs/SETUP.md section 5 |
| D8 | Accepted | The sandbox settings are a separate file, `settings.sandbox.json`. `install.py` merges it on macOS and Linux only. | Native Windows has no sandbox, so sandbox rules there would do nothing, and Bash allow rules would remove prompts that Windows needs. | One file for all OS: Windows would get rules that it cannot enforce. | none | README.md, docs/SETUP.md section 5 |
| D9 | Accepted | `setup-repo` treats a repo as a team repo when its `origin` is not under the user's own account. A team repo gets only local files that the global gitignore keeps out of git: `CLAUDE.local.md` and `.claude/settings.local.json`. | A tracked `CLAUDE.md` belongs to the team. Personal rules must not land in a team commit. | Write the files in every repo: it changes team files. Ask each time: the user would answer the same way each time. | none | GUIDE.md section 9 |
| D10 | Accepted | `repo_setup.py` commits on branch `chore/claude-forward`, skips a repo with uncommitted work, and never pushes. The skill asks before the push and the PR. | A setup change is a normal change: the user reviews it in a PR. A push is outward-facing, so the user decides. | Commit on the current branch: it mixes setup with other work. Push for the user: it breaks the ask-first rule. | none | GUIDE.md section 9 |
| D11 | Accepted | The plugin version in `claude/.claude-plugin/plugin.json` has a dated section in `CHANGELOG.md`. A guard change raises the version. | Claude Code copies a plugin once for each version, so without a new version the old guards keep running. A changelog section for each version tells the user what an update changes. | Update with no version change: users keep the old copy. | none | GUIDE.md section 16, docs/SETUP.md section 3 |
| D12 | Accepted | The loop records its evidence through hooks. The agent runs the verifier (`loopctl verify`) inside the sandbox, a PostToolUse hook records the evidence line, and the Stop hook judges it and commits or reverts. | Code that the agent edits runs in the sandbox. The agent cannot write the state, the evidence or the commits, so it cannot fake a pass. | The Stop hook runs the verifier itself: it needs a second sandbox profile to keep. An agent that declares its own stop: it can also write its own state. A model that judges: not deterministic, and it cannot commit or revert. | none | loop-engineering.md sections 5, 7, 11, 12 |
| D13 | Accepted | The usage stop reads a `rate_limits.json` file in the loop state folder. A status line script writes it. This repo ships no such script, so there is no usage stop until you add one, and the bundle says so. | Hook inputs do not carry `rate_limits`; only the status line input does. A missing file must not stop a loop or fake a limit. | Parse the output of `/usage`: a hook cannot read it. A manual stop only: you must watch your usage. | none | loop-engineering.md section 11.4 |
| D14 | Accepted | The hooks mirror the run data that `loopctl` needs into `.loop/run.json`. The mirror is protected and restored like the other mirrors. | Sandboxed commands cannot read the state folder, so `loopctl verify` and `bundle` cannot read the state file. | Open the state folder to sandboxed reads: it loosens a guardrail. Find the base commit with `git log --grep`: it gives the base but not the approved paths or the scores. | none | loop-engineering.md sections 7, 10, 11 |
| D15 | Accepted | A loop profile follows collaboration. A repo gets the strict work profile unless a rule maps it to personal. The tracked rule file ships empty. Your rules go in `~/.config/claude/loop-profiles.local.json`; the rule `{"owner": "self"}` maps every repo that only you can use. | A repo under collaboration needs the strict rules on any computer. Your own repos may use the personal rules. The plugin update replaces the tracked file, so your rules cannot live there. | A rule by machine name: it makes your own repos strict on a work computer. A third team profile: the work profile already is that profile. | none | loop-engineering.md sections 2, 16 |
| D16 | Accepted | During a loop, `guard_loop` denies every file-tool write outside the loop worktree. The bundle lesson goes to `.loop/lesson.md`, and `loop-approve` copies it to the main checkout. | File tools are not sandboxed, so without this rule they could write the main checkout or another repo. | Deny only the state folder and the plugin: the main checkout and other repos would stay writable. | none | loop-engineering.md sections 12.1, 13.1 |
| D17 | Accepted | During a loop, `guard_loop` denies `forge.sh pr-create`, and any repo creation through `forge.sh`, in both profiles, also for the trusted `forge.sh`. Its read-only commands (`whoami`, `kind`) stay allowed. | No push, PR or MR by the loop is a rule for every profile. The trusted `forge.sh` runs outside the sandbox, so it would push and open a PR. | Deny rule for the work profile only: a personal loop could open a PR. Deny every `forge.sh` call: the profile lookup needs its read-only commands. | none | loop-engineering.md sections 13.1, 13.2 |
| D18 | Accepted | The Stop hook sums the tokens of the whole loop again at each Stop, from the transcript lines at or after the confirm time, and writes the total to the state. | A sum is the same however often it is computed: a Stop that runs twice, a turn with no judge or a bundling turn cannot add a message twice. A stored transcript position would miss the turns that are not judged. | Add the usage newer than the last judged turn: a second counter to keep right. Count in `loopctl bundle`: the sandbox cannot read the transcripts. | none | loop-engineering.md sections 7, 10, 11.2, 11.4 |
| D19 | Accepted | The diff gate reads the whole loop branch from the fork point (the parent of the setup commit). A `setup-file` rule lets the setup add only checks and change the LOOP.md target. The rules `protected` and `skill-growth` read only the iterations. | The setup commit is written by the agent too. A stray file in it, for example a shell temp file with a secret, must meet the same secret scan and content rules as the iterations. | Refuse a stray setup file in `confirm` and scan only from the base: the content rules would still skip the setup. Stage only the files that the setup names: a missed name is silent. | none | loop-engineering.md section 15 |
| D20 | Accepted | Locking a live copy is opt-in. `guard_live_checkout` acts only on a clone that you list in `~/.config/claude/live-checkout.txt`. Claude then works in a worktree of that clone (`.claude/worktrees/`), and you deploy by merge and pull. Git that changes files there is denied inside the sandbox, because the sandbox would stop it halfway and leave a mixed tree. | A clone that other tools read as live config must not change while Claude works. Most users have no such clone, so the guard stays off. | Lock every clone: it breaks the normal flow of an ordinary repo. Document the risk only: edits to a live copy would stay possible with no prompt. | none | docs/SETUP.md section 3 |
| D21 | Accepted | The deny rules stop Claude's file tools from editing `.git/config` and `.git/hooks/`, in the current project and below `~/git`. For a repo in another folder, `repo_setup.py protect` writes absolute deny rules to the main checkout's ignored `.claude/settings.local.json`. `setup-repo` runs it first. | Auto mode let a file tool write a Git hook with no prompt, and an unsandboxed git runs hooks. A hook runs code on each commit. | A rule for every path: it breaks `git init` in temporary folders. A rule in each repo's committed settings: it does not reach a worktree session, and a team repo would need a commit. | none | GUIDE.md sections 6, 9 |
| D22 | Accepted | `repo_setup.py` judges and builds the setup from the committed files of the default branch (`origin/HEAD`, else `main` or `master`). A setup branch is ready only if its first commit is the setup commit and its files need no change by today's rules. Otherwise it is stale, and it is never rewritten. It warns about tracked personal files in every repo, also in a skipped one. | The checkout says nothing about what a merge brings. A report once called a branch ready when it held an older setup or unmerged feature work. | Switch the checkout to the default branch: it overwrites ignored files and fails beside other worktrees. Rebuild a stale branch: it can drop your commits. | none | GUIDE.md section 9 |
| D23 | Accepted | A hook that only advises starts with `py.sh --advisory`. With no working Python it exits 0. A guard starts without the flag and exits 2. | A tip must never block a prompt. A guard must never be off without a warning. | One launcher mode for all hooks: a missing Python would either block every prompt or turn every guard off. | none | docs/SETUP.md section 3 |
| D24 | Accepted | One package list, `packages/packages.json`, holds the `brew`, `apt` and `winget` names. `install.py` asks for a profile, then for each group, and installs nothing before a yes. Your trials and your own list stay in untracked files. | One list keeps the three managers equal. The ask-first rule covers machine-wide installs. Your own packages are personal. | A Brewfile for each OS: three lists drift apart. Install a whole profile on one answer: it hides what is installed. | none | GUIDE.md section 4 |
